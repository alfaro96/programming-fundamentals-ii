# Project context

This is the `code/` project of the **Programming Fundamentals II** repository: the JetBrains Academy course with the exercises and assignments of each unit. The lecture slides are in `../slides/`, with their own `CLAUDE.md`. Every path below is relative to this `code/` folder.

Students open it in IntelliJ IDEA with the JetBrains Academy plugin.

## Project layout

* `course-info.yaml`: the course: title, summary, and `content`, the ordered list of lessons.
* One folder per unit (lesson), named after it (`Introduction to Java/`, `Classes, objects, and methods/`...), with a `lesson-info.yaml` whose `content` orders its tasks.
* One folder per task inside each lesson, each with:
  * `task.md`: what the student reads.
  * `task-info.yaml`: the task type and its files.
  * `src/`: the Java sources.
  * `test/`: JUnit tests, for the tasks that are checked.
* `template/`, in the assignments handed out outside the plugin (as a PDF and a template on the virtual campus): the file students start from, which is the `src/` file with each placeholder replaced by its `placeholder_text`. It is listed in `.courseignore`, so the plugin leaves it out of the course.
* `latex/`, generated by `/latex` from `task.md`: `goals.tex`, `parameters.tex` and `tasks.tex`, which the instructor pastes into the Overleaf template to make the assignment's PDF. Same text and case as `task.md`, and bold only what `task.md` bolds. Ignored by git and listed in `.courseignore`; `task.md` is the source, so change it and generate them again rather than editing them.
* `.claude/commands/`: `/latex`, run with Claude Code started from this folder.
* `build.gradle`, `settings.gradle`, `gradle/`: Gradle build: Java 17, JUnit 4.12, `src/` and `test/` as source folders of every task.

## Task types

* `edu`: an exercise or assignment checked by the tests in `test/`, which are hidden from the student (`visible: false`).
* `output`: checked by comparing the program's output with the expected one.

## Rules

* **Placeholders are character offsets.** In `edu` tasks, `task-info.yaml` marks the part the student writes with an `offset` and a `length` counted in characters of the source file. Editing that file outside the IDE shifts them: update `offset`, `length` and `placeholder_text` in the same change, or say plainly that the instructor must fix them from the JetBrains Academy plugin. If the task has a `template/`, update it too, so that it is still the `src/` file with its placeholders filled in.
* A new task or lesson has to be listed in the `content` of its `lesson-info.yaml` or `course-info.yaml`, or the JetBrains Academy plugin will not show it.
* All Java code must compile with Java 17 and every `edu` task must pass its own tests with the reference solution.
* Keep the level of the slides: students come from C and meet Java syntax in unit 1. Do not use constructs the unit has not introduced yet.
* `build/`, `out/`, `doc/` (Javadoc), `latex/`, `.gradle/` and `.idea/` are generated and ignored by git; never edit them.

## Javadoc

Students read the Javadoc of the solutions and templates as the model for their own, so every comment follows these rules:

* **What is documented**: every class and every method, `main` and test methods included, and every field. A template documents what it shows (at least `main`), so students have an example to follow.
* **Summary**: the first sentence says what the class or method does, in the third person and ending with a period ("Computes the sum...", "Checks...", not "This method computes..."). More detail goes in later sentences or in `<p>` paragraphs.
* **Tags**, in this order and after a blank ` *` line: `@param` for each parameter, in the order they are declared; `@return` in every non-`void` method; `@throws` for each exception the method throws or declares; in classes, `@author` (`Juan Carlos Alfaro Jiménez` in solutions and tests) and `@see` when another class is related. Each tag's description starts in lowercase and ends with a period (`@param n the last integer to add.`).
* **It is HTML, not Markdown**: never backticks, `**` or `$...$`.
  * Code, identifiers, literals and expressions go in `{@code ...}`: `{@code n}`, `{@code for}`, `{@code sum1(11)}`, `{@code true}`. It also escapes `<`, `>` and `&`.
  * References to a class, method or field go in `{@link ...}` (`{@link Sum}`, `{@link #sum1}`, `{@link Sum#sum2}`), at least the first time they appear.
  * Formulas are written in HTML: variables in `<i>`, `&hellip;` for an ellipsis, `<sup>`/`<sub>` for exponents and subscripts, and `&lt;`, `&gt;`, `&amp;` for those symbols outside `{@code}` (`<i>n</i>(<i>n</i> + 1) / 2`, `0 + 1 + &hellip; + <i>n</i>`).
  * Paragraphs with `<p>` and lists with `<ul>`/`<li>`, never blank lines or `*` bullets on their own.
* **It must be valid**: `javadoc -Xdoclint:all` must give no errors and no warnings on solutions and tests. The only warning allowed is the one for the default constructor in a class that declares none, when the unit has not introduced constructors yet. A template is checked with its `TODO`s filled in, which is the solution, so the comments it shows must not `{@link}` to anything the student has yet to write: name it with `{@code}` instead.
* The `task.md` files, on the other hand, are Markdown: there code goes in backticks and formulas in `$...$`. When a task asks students to write Javadoc, it explains these same rules at their level.

Each lesson goes with a unit of the slides, which hold the examples: the lesson has only exercises (`edu` and `output`), problems of their own that only have to stay within what the slides introduce. See "Keeping `slides/` and `code/` in step" in the repository's `CLAUDE.md` before renaming, adding or reordering anything; if a slide links to an exercise, renaming its folder means updating that link.
