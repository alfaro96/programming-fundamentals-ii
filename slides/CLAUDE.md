# Project context

You're helping build the slides for **Programming Fundamentals II** (Java), in beamer, compiled with latexmk and XeLaTeX (TeX Live). The instructor will feed you loose notes, jotted-down ideas, or descriptions of what they want to cover, and your job is to turn that into well-formed slides that stay consistent in style and structure with the rest of the course.

You're not just a text-to-LaTeX converter: you decide which slide type fits best, whether the content should be split across several slides, and where it belongs within the unit. If something is ambiguous, ask before inventing technical content (code that wasn't requested, examples that weren't mentioned, etc.).

## Project layout

This is the `slides/` project of a repository that also holds `code/`, the JetBrains Academy course with the exercises and assignments (it has its own `CLAUDE.md`). Every path below is relative to this `slides/` folder, and every command runs from it. Building needs a TeX Live distribution (MacTeX on macOS) with `latexmk` and `xelatex` on the PATH.

* `beamer/units/unit_N-short_name/main.tex`: one folder per unit, e.g. `beamer/units/unit_1-introduction_java/`. The folder name is fixed: lowercase `unit_`, a single-digit number, a hyphen, and a short `snake_case` name; the scripts sort by it and name the PDFs after it. A two-digit unit would sort right after `unit_1`, so if a tenth-plus unit ever appears, say so instead of inventing `unit_10`. A unit's images go in its own folder, next to `main.tex`.
* Every `main.tex` starts the same way: `\providecommand\deckoptions{aspectratio=169}`, `\documentclass[\deckoptions]{beamer}`, `\input@path{{../../}}` so it finds the shared files, then `\input{packages}`, `\usepackage{style}`, `\input{commands}`, its `\title` and `\subtitle`, and `\input{cover}`. Copy the head of unit 1.
* `beamer/palette.tex`: the palette and the colors by role, and `beamer/codefont.tex`, the code font (JetBrains Mono, from `fonts/`), both shared by the slides and the statements (they are part of the styling: the rules for `style.sty` apply to them).
* `beamer/style.sty`: ALL the rest of the visual styling: the fonts, the sizes, the title and slide number, the contents slides and every component. Never put loose styling in a unit (no `\color{...}` with a hex, no `\fontsize`, no hand-tuned `\vspace` to line things up); if the instructor asks for a visual change, edit only this file.
* `beamer/commands.tex`: the course's name, author and degree (the only place they live) and the inline macros a unit writes with: `\code`, `\key`, `\state`, `\behavior`, the verdict marks and `\todo`.
* `beamer/packages.tex`, `beamer/cover.tex` and `beamer/fonts/` (JetBrains Mono, with its license; Inter comes with TeX Live).
* `statements/`: the statement PDFs of the exercises and laboratory assignments in `../code/`, from the LaTeX that `/latex` writes in each task's `latex/` folder: `exercise.tex` and `assignment.tex` `\input` it, styled by `statement.sty` (A4, plain, the text in LaTeX's own font, Latin Modern, the code in the slides' JetBrains Mono, from `codefont.tex`, with the slides' palette, from `palette.tex`, and the course name from `commands.tex`). `scripts/statements.sh` compiles one per task, numbered as in `code/` (assignments from 0, across the course), into `production/exercises/<unit>/<N>.pdf` and `production/assignments/<unit>/<N>.pdf`; a unit's lesson is the folder of `../code/` named after its cover title.
* `scripts/beamer.sh` and `scripts/statements.sh` (`npm run pdf`), `scripts/preview.sh` (`npm run preview`) and `scripts/index.mjs` with `site/site.css` (`npm run build`, the index page of the web version).
* `production/`: generated and ignored by Git: `class/` and `print/` (the slides), `exercises/` and `assignments/` (the statements), `aux/` (latexmk's auxiliary files), `web/` (what GitHub Pages publishes) and `preview/` (PNGs of the pages).

## Current visual style

Defined in `beamer/style.sty` and, its palette, in `beamer/palette.tex`. Everything sits on the white slide background, code blocks and terminals included (the slides go through a projector). The instructor's palette is defined once, in `palette.tex`, and every other color points at it through a name for its role (e.g. `colorHeading` for titles, `colorAccent` for the main accent, `colorAccentTwo` for code). The palette may change or grow, so read that block for the current colors instead of assuming them, and refer to colors by role, not by name. Reach for the palette first; when a color it lacks is really needed, define one that fits with it as a named color in `style.sty`, never a loose value in a unit. If the instructor hasn't given styling instructions yet, don't change it: only touch it when explicitly asked, and then change the values under "Deck geometry", "Palette" and the size sections rather than rewriting the templates.

Sizes are in px of a 1920 px wide canvas (`\px`) or in ems of the slide font (`\slideem`, `\slidefont`), so the whole deck scales as one.

## Slide types

Every slide is a `frame` with a title and a one-line subtitle (`\begin{frame}{Title}{Subtitle}`); a frame with code is `[fragile]`. Steps are beamer overlays: `<2->` on a card, a takeaway or `\uncover`, and `steps={...}` on a code block.

1. **Title**: the cover, from the unit's `\title{Unit N: Unit name}` and `\subtitle`, built by `\input{cover}`.
2. **Concept**: an idea or definition as cards (`\begin{cards}` with one `\begin{card}{Title}` per idea), never a bullet list. Cards are blue; `[warn]` (orange) marks something that works but needs care and `[error]` (red) something that does not compile or fails, as the verdict marks do. Use them sparingly, or the color stops meaning anything. The one other pair is `state` (plum, what an object holds: its data) and `behavior` (berry, what it does: its operations), as tones of cards, code notes and marks and as the colors of `\state{...}` and `\behavior{...}`, only where a slide sets the two side by side; from unit 2 on, those colors always mean data and operations, never orange (take care) or teal (it works).
3. **Code**: the code block is the protagonist. Use `steps={1|3-5}` when it makes sense to walk through the code incrementally, instead of surrounding it with explanatory text.
4. **Comparison**: two versions side by side (typically C and Java) in `columns`, in steps: the known one alone, then the other next to it (`uncoverenv`), then only the lines that differ highlighted (`diff`), with the takeaway. When there is nothing to mark, the takeaway comes right after the second version.
5. **Exercise**: a challenge or question for the class during the lecture; the solution goes on the frame after it, not on the same one. Not to be confused with the unit's exercises in `../code/`, which students solve on their own.
6. **Summary**: unit wrap-up, the frame `{Unit summary}{What to take away from this unit}` in every unit, as `\begin{recap}`, one `\recapitem<step>{Section}{Sentence}` per section, in order: drawn as the contents slides, each section lights up on its step with its sentence beside it.
7. **Contents**: the unit's index, repeated before every section with that section highlighted. Beamer builds it from the unit's `\section{...}` commands: write one before each section, nothing else.

If the notes don't make it clear which slide type fits, pick the best match and say so explicitly when you're done (e.g. "I built this as a code slide because the focus is on the loop, not the concept"). Don't decide silently.

## Components

Defined in `beamer/style.sty`, each with a comment on how to use it; units 1 to 5 use every one of them, so copy from their slides.

* **Takeaway** (`\takeaway<step>{...}`): the slide's one-line conclusion, highlighted, with the key words in `\key`. Written after the content, it always sits at the bottom left of the slide, on its own (nothing goes before it to place it), and the content stays centered in the space above it; a frame the instructor wants with its content at the top takes beamer's `[t]`. It closes the whole slide, so on its step no code is highlighted: a code block that steps ends in an empty step (`steps={4-6|8-11|9|}`).
* **Cards** (`cards`, `card`): see Concept. `\begin{cards}[2]` sets them in columns, a row as tall as its tallest card.
* **Code** (`codeblock`, `console`, `consoleerror`, `\blocktitle`): `\begin{codeblock}[steps={...}, steps from=2, compact]{java}` (or `{c}`). `lines={1|2}` writes it line by line, the lines after the given one hidden on each step, so the class can be asked for the next (e.g. "One name, several versions"). A step is a comma list of lines and ranges; an empty step leaves the block plain and `none` fades it whole, for a block with nothing to mark while the one beside it steps; `diff` highlights without fading. `add={9/3}` (line/step) adds a line on a step: before it the block leaves it out and numbers the rest in order, and the lines in `steps`, `marks` and `strike` follow the rows they take on each step, numbered as in the full block; print shows it. `strike={9/3}` crosses it out, in the tone of errors, from that step: a line that does not compile, added with the error note that points at it, in the colors of any other (e.g. "Static methods", "Final attributes", "Creating with the constructor"). A comment that stands for code left out (`// the rest of the class, as before`) goes after all the code shown, never between two parts of it nor before them; in C, where what is used has to be declared first, the comment for a struct or functions goes at the top (e.g. "In Java: the operations") (e.g. "Static methods"). `compact` and, smaller still, `dense` fit long or many lines; `packed`, smaller again, only two whole classes side by side with their notes under them (e.g. "Two classes, by hand"). `console` is what a program prints, `consoleerror` an error, tinted red. `\blocktitle` puts a file or column name over a block. `\begin{boxrow}` around a `columns` row of boxes (card, code, console) makes them as tall as each other, their content centered (e.g. "Printing to the screen"); code in it takes no steps or marks. Code and cards (or notes) stepped together count the same overlays (e.g. "Our first program" and "Comments").
* **Question** (`\question{Question}<step>{Follow-up}`): a question to the class on a frame of its own, with no title, large and centered, right before the slide whose idea answers it, so they think about it first. Usually one question; the follow-up, on its step, only when it adds something, and any hint goes in the note. Few of them, where a new idea really starts (e.g. before "Platform independence", "Classes and objects" and "Constructors").
* **Code notes** (`codenotes`, `\codenote`, and `marks` on a `codeblock`): what a slide explains about a block of code, tied to its lines. `marks={1/3, 6-7/4/state}` (line or range/step/tone) puts a numbered disc at the end of each line from its step on, numbered in order from 1, or from `marks from=2` for a block whose notes go on from the one beside it; a fourth field gives a disc its own number, and the next ones go on from it, for a block that shows only some of the notes (e.g. `7+10/5/error/3` in "Creating with the constructor", whose blocks share note 1 and have one more each); places joined by `+` repeat a number, for a note about several parts of the block (e.g. `1+2-4+6-14/3`, the naming conventions in "Attributes and methods"), and a disc on a place already taken sits to the left of the one there; a range keeps the column, and a disc on one of its lines that would touch its disc or its bar moves left of them (e.g. "The wrong cast"), so consecutive lines with one note are a range (`2-3`), never `2+3`; in print a range (`2-4`) also gets a bar in the disc's tone left of its discs, so it shows which lines it covers (in class the step's highlight does); and `\begin{codenotes}[columns]` with one `\codenote<step>[tone]{Title}{Text}` per mark sets the explanations under or beside the code, with the same numbers and no background, so the code stays the protagonist. A tone colors a disc and its note's title, as a card's: `state` and `behavior` for data and operations, `error` for what does not compile. `\codenote*` has no number, for a remark about the block that points at no line in it (e.g. "Static attributes"). A disc must not cover code: on a long line, make the block `dense` or the column wider. Use it in place of cards when the cards would each explain a line of the block (e.g. "Our first program" and "Comments"). The numbers are for pointing at code; a list of rules with nothing to point at goes in a data table (e.g. "Naming variables").
* **Flow diagram** (`flow`, `\flowbox`, `\flowarrow`, `\flowover`, `\flowbranch`, `\flowcaption`, `\flowconsole`, `\flowsnippet`, `\runicon`): boxes in columns 1, 3 and 5 joined by arrows with a label over and a command under, an arrow over the row from end to end, up, across and down (the IDE's Run button, `\runicon`), an optional dashed branch to a lower row, captions under the boxes; the slide's takeaway goes after the diagram. Under a box, as wide as it, goes what it holds or prints: a console block (`\flowconsole[error]{box}{lines}`, which a branch or a caption can start from as `<box>console`), or a small code block (`\flowsnippet`, built first in `\begin{lrbox}{\flowsnippetbox}` with `\begin{codeblock}[snippet]`). E.g. "Platform dependency": the source under Source code, the hex dump under Machine code, and each output under its result. Tones: `source` (blue, what the student writes), `output` (gray, what the compiler generates), `ok` (teal, it works) and `error` (red, it fails); orange is kept for warnings and the takeaway's border. Every command takes a step and TikZ options, so a part can fade on a later step (`\flowbox<2->[dim on=<4->]`): one row tells both what the user sees and what happens underneath, without a second diagram. E.g. "Platform dependency" and "Java's execution model".
* **Toolbox** (`toolbox`, `toolgroups`, `\toolgroup`, `\tool`, `runtime`, `\toolpart`): a block of tools in columns, with an optional block nested inside. E.g. "The Java Development Kit" and "The JDK and the JRE".
* **Data table** (`datatable` with `\tablehead`, `\tablerule`, `\grouprule`, `\partrule`, `\tablelabel`, and the columns `Y` for text, `M` for marks and `C` for marks that share the width, in a table with no text column, e.g. "Four access levels"): rows split by hairlines and groups by a heading-blue line. When the rows are examples asked the same questions, all of them show from the start and each row's answers fill in at once with `\uncover`; when each row is a question of its own, its label shows first and its answers on the next steps (e.g. "Arrays in C and Java"). A table whose rows are lines of the code block beside it goes by their numbers, and highlights each line alone on the step before its row, to ask about it, and while its row fills in, the number standing for a disc (e.g. "What runs?"). A reference table shows by groups (e.g. "The eight primitive types", and "Naming variables", whose rules and conventions are two groups); `\begin{datatable}[dense]` sets one too long for the slide in smaller text and rows (e.g. "Java's exceptions"). A cell too long for its column goes on several lines with `\celllines{first \\ second}`, at the same size and centered on the row's other cells, broken where Java allows it (e.g. the constructor call in "Which one runs?").
* **Verdict table** (`datatable` with `\markok`, `\markcaution`, `\markerror`, `\marknone`, and `\markno`, a plain gray no, for what simply does not run or is just no, e.g. a test that is false as expected in "`getClass`"): one row per example, a question per column answered with a mark. E.g. "Valid or not?", "Safe or not?", "When does it run?".
* **Keyword grid** (`\keywordgrid<step>{a, *b}`): words in five columns; the starred ones dim and are crossed out from the step. E.g. "Reserved words". `\codeunused<step>{name}` is a `\code` that does the same, for names in a table the course leaves aside (e.g. "Java's exceptions", a class and its subclasses per row, one row per step, then the uncommon ones crossed out).
* **Phones** (`phones`, `\phone`, `\phonegroup`, `\phonearrow`): the bank's app on phone screens, the running example of unit 2. `\begin{phones}[large]` (alone on the slide), default (beside notes or over a takeaway) or `[small]` (under captions) holds a row of `\phone[holder=..., initials=..., iban=..., balance={...}]`; `template` empties it into the class, with slots for the data, the buttons in the tone of operations; `tones` gives an object those same tones (its data in that of data, its buttons in that of operations) to match it with its class; `data mark`/`operations mark` with their `... on` steps number them for notes beside it; `rate` with `rate on`, `lock on` and `tap on` add the interest rate, a padlock by the IBAN and a pressed Deposit on a step (in the color of operations). `\phonegroup<step>{Title}{Caption}{phones}` and `\phonearrow<step>` set a class next to its objects. E.g. "Three bank accounts", "The template they share", "Classes and objects". `\devicephone[icon=light, kind=Light, name=..., power=On, label=..., value=..., bar=80, set=...]` is the home app of unit 3 in the same row, a device's screen: `template` with `data mark`, `operations mark`, `own data mark` and `own operation mark` (the dashed boxes of what each kind adds, in the tones of data and of operations), or of another tone with `own data tone` and `own operation tone` (e.g. `warn` for a value that should not be, beside a note of that tone), `bar to` with `bar on` and `tap on` (the set button pressed); `\homephone{\hometile[icon]{Name}{Status}...}` is its first screen, a tile per device over an All off button. `\tilemark<step>[tone]{n}` right after a tile puts a numbered disc by it, a second one beside the first (e.g. "One status per tile"). The phones share one case, `\pf@phoneshell`. E.g. "Three smart devices", "What they share", "Brightness: 250%", "One status per tile".
* **Changed values** (`\changed<step>{old}{new}`, `\marked<step>{text}`, `\highlight{text}`): a value that changes on a step, or one the slide points at, in bold and in the color of emphasis, not tinted, which in a phone or a diagram would read as one more box; they work inside phones, memory diagrams and tables. E.g. "One rate for every account", "Two variables, one object".
* **Memory diagram** (`memory`, `\memvar`, `\memref`, `\memnull`, `\memobject`, `\memstring`): the stack next to the heap, next to the code that builds them, stepping with it. A variable holds its value (`\memvar`), a reference with an arrow to its object (`\memref`, `\memref[Type]` with the variable's type over its cell, as the class over an object, when the two differ, e.g. "A `Device` variable"; `\memref*` bends its arrow to the middle of the object, for two references to one object far apart, e.g. "A cast to `Light`") or none (`\memnull`, and `\memnullvalue` for an object's attribute that is `null`); objects (`\memobject{name}{row}{Class}{field/value, ...}`) and strings (`\memstring`) are named before the arrows that reach them. `memory[rows]` gives the stack's rows; both frames grow to the taller side and center both, so no row is left empty. A state that a later step replaces takes `<n| handout:0>`, so print shows the last one. E.g. "What new does in memory", "Changing one of them".
* **Widening chain** (`\widening<step><step>{byte, short, int}{Title}{Sentence}{Title}{Sentence}`): types joined by arrows both ways, widening (teal, to the right) explained over the chain and narrowing (orange, to the left) under it, each in its arrows' color. E.g. "Type conversion".

* **Class diagram** (`classdiagram`, `\classbox<step>{id}{column}{superclass}{Class}{attributes}{methods}`): classes as in UML, the name over its attributes (in the tone of data) and methods (of operations), each part only when it has something; a class given its superclass's id sits under it with the hollow-headed arrow of inheritance; types as IntelliJ draws them (`name: String`, `setBrightness(int): void`), no visibility before "Private attributes"; an interface's name is `\interfacename{List}`, with «interface» over it, and `\classbox*` is a class that implements the interface above it, its arrow dashed, as in UML (e.g. "The collections framework"). `\classunused<step>` right before a `\classbox` dims the class and its arrow from the step and puts a cross over its box, for a part of a hierarchy the course leaves aside (e.g. sets and maps in "The collections framework"). `\classmark<step>[tone]{above|below}{id}{n}` puts a numbered disc centered over a class's box (a superclass, whose arrows leave from its bottom) or under it (a subclass) and `\classwrong<step>[tone]{subclass}{superclass}{n}` an inheritance that is not allowed, dashed in its tone (warn by default), with its disc (e.g. "Not every device has a level"); `\inheritmark<step>[tone]{subclass}{n}` right of the arrow that leaves a subclass (one per subclass), halfway up its vertical stretch, or of the line up to the arrowhead when it is the only subclass (`\inheritmark*` over the stretch across that is that subclass's alone, when a `\classwrong` leaves from its turn too), for the notes beside the diagram, which always point at it that way. E.g. "Superclass and subclasses", "Hierarchies", "`Object`".
* **File explorer** (`explorer`, `\explorerrow<step>[marked on]{depth}{folder or java}{Name}`): a project's files as an editor shows them, `marked on` highlights a row on those steps (with a note of its own, as any highlighted line). Under a `\blocktitle`, so it lines up with the code blocks beside it. E.g. "Packages".

A component a new unit needs and `style.sty` lacks is built the same way as the ones above (TikZ or tcolorbox, sizes from the style, steps as overlays) and added to this list. Code with its output per row is a `boxrow` with a card, a `codeblock` and a `console` (e.g. "Printing to the screen"); a verdict is a `datatable` with marks. Stacked rows are split by `\boxrowgap`, closer than between blocks, so they read as one list.

## Content rules

* Keep text light per slide: if you notice you're adding more than ~5-6 cards or items, or a code block over ~15-18 lines, consider splitting it into several frames instead of shrinking the font or cramming the layout.
* All example Java code must compile and make sense as shown; avoid pseudocode unless the instructor explicitly asks for it.
* From unit 2's "Constructors" on, where `this` is introduced, code reaches the object's own attributes and methods through `this` (`this.balance`, `this.deposit(amount)`) even with no name clash; static ones go by their name alone. The slides before it write them without `this`, which they have not seen yet. `../code/` follows the same rule.
* From unit 3's "Private attributes" on, attributes are `private` and classes, constructors and methods `public`, unless the slide is about another modifier. The slides before it use no modifiers but `public static void main`. `../code/` follows the same rule.
* Code that belongs to a class (attributes, constructors, methods) is shown as the whole class, with what does not matter on the slide folded into one comment: the members it leaves out when they are few and named (`// constructor and getter, as before`, `// turnOn and turnOff, as before`), or `// the rest of the class, as before` when it would only list kinds of member (attributes, constructor, methods); never a method on its own. Code that uses the classes is a whole `Main` the first time in a unit, and just the statements after that (they go inside `main`). A file name over each block (`\blocktitle{\code{Light.java}}`) when a slide shows more than one file.
* Code inside a sentence goes in `\code` (its rounded tint sets it apart from the words around it): in cards, notes, tables, takeaways, captions, block titles and frame titles. Code that is a label of a diagram or a component goes in plain code font, with no tint: a file name in a flow box (`\texttt{hello.c}`), a command under a flow arrow, a tool's name in the toolbox, the words of a keyword grid or a widening chain, and what a console prints.
* A method named in text, on the slides and in the speaker notes, goes without parentheses (`\code{toString}`, `\code{status}`), as a name, not a call; they stay in code itself (a call with its object, `device.status()`; a header; a diagram's `turnOn(): void`), in `\code{super()}`, which tells the constructor call from `super.` and `super(...)`, and in a compiler message quoted as Java prints it.
* Quotation marks in text, on the slides and in the speaker notes, go in `\enquote{...}` (csquotes), never typed straight (`"..."`), so they come out curly and copy as such; quotes inside code stay as the code writes them.
* Use speaker notes (`\note{...}` at the end of a frame, one paragraph) for the extended explanation the instructor will say out loud but doesn't want on screen. It's the natural place to park context from raw notes that shouldn't appear on the slide itself.
* An exercise list ("Exercises", at the end of the section after which some of the unit's exercises in `../code/` can be solved) is a `datatable` with an `Exercise` and a `What it practices` column, one row per exercise, its name an `\href` to the task's folder on GitHub (e.g. unit 2).

## Implementation rules (no patches, no anti-patterns)

These are non-negotiable. If a request seems to need one of the things forbidden here, the structure is wrong: stop and say so instead of forcing it.

**Styling lives in `style.sty`.** A unit writes content and calls components; it never sets a color, a font size or a spacing by hand. Text repeated across every unit (course name, author, degree) lives in `commands.tex`.

**Leave beamer's defaults alone.** Frames are centered, as beamer centers them; steps use beamer's overlays (`<n->`, `\uncover`, `uncoverenv`, `\only`); the contents slides come from `\section`. Do not patch beamer's internals or compensate for its spacing; if something needs it, the markup is wrong. The theme sets beamer's templates and colors, which is what a beamer theme is for.

**Real layout, not tuned spacing.** Lay out with `columns`, `cards`, tables and the components. A stack of hand-tuned `\vspace` values that happens to land in the right place is a patch: it breaks the moment the text length or the page changes. The gaps a unit writes are named in `style.sty`: `\blockgap` between a block and the next one, `\notesgap` between code and the notes or table that read it, and `\boxrowgap` between stacked box rows.

**No magic numbers.** Any value that sizes or positions something gets a named macro or length in `style.sty` with a comment saying what it's for, in canvas px or slide ems.

**Comment and formatting style.** Keep comments short: say what something is or warn about a trap, never a paragraph explaining the reasoning. One line when it fits in about 100 characters; if it really needs more, a second line split at a natural break. One space before a trailing comment in shell and JavaScript, two in YAML (yamllint's default), never padding to align them in a column. Section headers in `style.sty` are `% % % % % % % % % % Name % % % % % % % % % %`. Double quotes in JavaScript. No em dashes.

**One source of truth.** Anything that appears on more than one slide is defined once. Never solve repetition by copy-pasting into each unit.

**Two PDF versions, one source.** The class PDF is 16:9 with a page per step; the print PDF is 16:9 too, with `handout`: every step visible on one page, and code shown plain. `scripts/beamer.sh` builds both from the same `main.tex` by setting `\deckoptions`. Every slide has to work in both, so lay a slide out for its last step.

**Verify, then say what you couldn't verify.** Before claiming a change works, build it (`npm run pdf`) and look at it: `npm run preview -- class <unit>` and `npm run preview -- print <unit>` put every page as a PNG in `production/preview/<version>/<unit>/`. Read the pages the change touches, the last step of each frame and the print version too, and check the build log for overfull boxes. Say plainly what you could not check.

## Expected workflow

1. The instructor gives you loose notes or dictates what they want to cover, sometimes via `/new-slide`, sometimes pasted directly in chat.
2. You decide the unit, the slide type, and generate it in its place within the unit: inside its section, before the summary (if the unit doesn't exist yet, create it with `/new-unit` or ask for its number/name before improvising one).
3. The instructor reviews the PDFs and asks for specific tweaks, to content or style (`/change-style`).
4. In the same turn, bring the unit's lesson in `../code/` in line with what changed, as "Keeping `slides/` and `code/` in step" in the repository's `CLAUDE.md` describes, and say what you changed there. `/sync-unit` checks a whole unit at once.

Don't renumber or reorder existing slides without being explicitly asked: the instructor may already have rehearsed the lecture around that order.
