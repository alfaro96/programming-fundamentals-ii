# Project context

You're helping build the slides for **Programming Fundamentals II** (Java), in reveal.js. The instructor will feed you loose notes, jotted-down ideas, or descriptions of what they want to cover, and your job is to turn that into well-formed slides that stay consistent in style and structure with the rest of the course.

You're not just a text-to-markdown converter: you decide which slide type fits best, whether the content should be split across several slides, and where it belongs within the unit. If something is ambiguous, ask before inventing technical content (code that wasn't requested, examples that weren't mentioned, etc.).

## Project layout

This is the `slides/` project of a repository that also holds `code/`, the JetBrains Academy course with the exercises and assignments (it has its own `CLAUDE.md`). Every path below is relative to this `slides/` folder, and every command runs from it.

* `content/unit_N-short_name.md`: one file per unit/lecture, e.g. `unit_1-introduction_java.md`. This naming is fixed: lowercase `unit_`, a single-digit number, a hyphen, and a short `snake_case` name. `reveal-md` concatenates the files in alphabetical order, so the number is what keeps the units in order. A single digit allows `unit_0` to `unit_9`; a two-digit unit would sort right after `unit_1`, so if a tenth-plus unit ever appears, say so instead of inventing `unit_10`.
* `content/assets/`: images, one subfolder per unit named as its file (`content/assets/unit_1-introduction_java/`), referenced from the slides as `assets/unit_1-introduction_java/image.png`. Anything shared by every unit goes straight in `content/assets/`. Keep the folder even when empty (`.gitkeep`): `reveal-md.json5` copies it and the build fails without it.
* Within each file, slides are separated by `---` (horizontal) and `--` (vertical). A new idea starts a horizontal slide; a slide that continues the same point goes below it: the answer to a question, the code of what the slide above showed on the phones or in a diagram, the problem and its fix, a variation or a follow-up (e.g. "Three bank accounts" with the template and the C version below it; "Platform dependency" with "Platform independence" below it).
* `theme/custom.css`: ALL visual styling (colors, background, typography, code block styling) lives here as CSS variables in `:root`. Never put loose styling inside a slide `.md` file; if the instructor asks for a visual change, edit only this file.
* `theme/*.js`: what the slides build at runtime: the cover, the contents slides, the print handout and the drawing buttons (`theme/draw.js`, which sets up the chalkboard plugin).
* `theme/reveal.html`: the page around the slides, reveal-md's own template with two changes: `viewport-fit=cover`, so the arrows and the drawing buttons keep clear of a tablet's screen edges, and `{{{markdown}}}` at column 0, because reveal's markdown plugin strips the first line's indent from every line, so code indented that deep (12 spaces in the original) loses it. Its first comment names the reveal-md version it was copied from: if reveal-md changes its template, copy the new one and make both changes again.
* `theme/vendor/`: third-party plugins copied as they are, with their license; never edit them, adjust them from `theme/draw.js` and `theme/custom.css`.
* `templates/`: one mold per common slide type in this course. Use them as a starting point and adapt the content; don't copy them literally with placeholders left in.

## Current visual style

Defined in `theme/custom.css`. Everything sits on the slide background, code blocks and terminals included (the slides go through a projector). The instructor's palette is defined once in `:root`, under "Palette", and every other color points at it through a variable named for its role (e.g. `--color-heading` for titles, `--color-accent` for the main accent, `--color-accent-2` for code). The palette may change or grow, so read that block for the current colors instead of assuming them, and refer to colors by role, not by name. Reach for the palette first; when a color it lacks is really needed, define one that fits with it as a named variable in `:root`, never a loose hex in a rule. If the instructor hasn't given styling instructions yet, don't change it: only touch it when explicitly asked. If they ask for a change ("lighter", "different accent color", "make it match X"), edit only the variables in `theme/custom.css`'s `:root`, never rewrite the whole file or touch the structural rules.

## Slide types (`templates/`)

Every slide has a title and a one-line subtitle (`##` then `###`).

1. **Title** (`title.md`): opens a unit with `## Unit N: Unit name` and a subtitle.
2. **Concept** (`concept.md`): an idea or definition as rule cards, one idea per card; never a bullet list. Cards are blue; `rule-warn` (orange) marks something that works but needs care and `rule-error` (red) something that does not compile or fails, as the verdicts do. Use them sparingly, or the color stops meaning anything. The one other pair is `rule-state` (orange, what an object holds: its data) and `rule-behavior` (teal, what it does: its operations), only where a slide sets the two side by side; from unit 2 on, those colors always mean data and operations.
3. **Code** (`code.md`): the code block is the protagonist. Use step-by-step line highlighting (`[1|3-5]`) when it makes sense to walk through the code incrementally, instead of surrounding it with explanatory text.
4. **Comparison** (`comparison.md`): two versions side by side (typically C and Java), in steps: the known one alone, then the other next to it, then only the lines that differ highlighted, with the note. When there is nothing to mark, the note comes right after the second version.
5. **Exercise** (`exercise.md`): a challenge or question for the class during the lecture; the solution goes in a vertical sub-slide (`--`) below it, not on the same slide. Not to be confused with the unit's exercises in `../code/`, which students solve on their own.
6. **Summary** (`summary.md`): unit wrap-up as a grid of cards, one per section.
7. **Contents** (`contents.md`): the unit's index, repeated before every section with that section highlighted. The list is written once, in the first one; `theme/contents.js` builds the title, the subtitle and the copies.

If the notes don't make it clear which slide type fits, pick the best match and say so explicitly when you're done (e.g. "I built this as a code slide because the focus is on the loop, not the concept"). Don't decide silently.

## Components

Built for a specific need, with no template on purpose: reuse one when the same need comes back, and don't force it where it doesn't fit. Its classes are in `theme/custom.css`; copy the markup from a slide that already uses it (the ones named here are examples from unit 1; if one has changed, search `content/` for the class).

* **Stage** (`stage`, `stage-body`, `stage-top`, `stage-note`): the slide fills the canvas, its block is centered (`stage-body`) or kept at the top (`stage-top`), and the takeaway sits at the bottom (`stage-note`). Used by almost every slide.
* **Code with cards**: a card appears with the lines it explains. The code goes as raw `<pre><code data-fragment-index="0">` and the cards count from 0 too (see the comment in the slide). E.g. "Comments" When the bottom note appears, the code highlights what the note sums up (a final step at the note's index); if it sums up the whole block, that step is empty, which leaves the block plain, as on entry, rather than every line highlighted. Only in a paired walkthrough does an empty step dim a block instead. E.g. "Static attributes" and "Attributes and methods".
* **Paired walkthrough** (`code-pair`, `code-over-cards`): C and Java stepped together from 0, with the cards under them (`rules-pair`); a block with nothing to mark in a later step (an empty step in `data-line-numbers`) dims whole, while an empty first step leaves it as it is (C alone, on entry). Inside raw `<pre>`, and in the HTML of cards and tables (`List&amp;lt;Device&amp;gt;`), write `<` as `&amp;lt;`: the entity is decoded once before the HTML is read. Reveal renumbers the fragment indices without gaps before the code steps exist, so every index a code step uses must also be used by some other element on the slide. E.g. "Our first program: `Hello.java`".
* **Flow diagram** (`flow`): boxes joined by arrows, with an optional branch; `flow-layers` stacks a simple flow and a detailed one, in either order, split by a `flow-divider` (e.g. "Under the hood", "On the surface"), and `flow-long` stretches an arrow to the last box. E.g. "Platform dependency" and "Java's execution model".
* **Terminals** (`terminals`): consoles of different machines, one under the other, no line numbers. No slide uses it at the moment.
* **Code and output** (`runs`): one example per row, a card, its code and what it prints, rows as tall as the tallest (`runs-fit` makes each row as tall as its own content, when one row's code is much longer). E.g. "Printing to the screen". `code-run` puts one program over its output, which shows with the code's last step (repeat the last highlight step for it; see the comment in "Working out the initials"). When the code prints on several steps, each print is marked alone first, to ask what it prints, and its line of output shows on the next step: the output box is a fragment at the first print's index, a raw `<pre><code class="nohighlight hljs console" data-noescape>` whose later lines are `<span class="fragment">` at the next indices, and the note gets its own last step (e.g. "Two equal lamps?"). `output-swap` stacks two outputs in one place, so one can give way to the other, such as an output to the error a new line causes (e.g. "A `Device` variable"). An error a program or the compiler prints goes in a `console-error` wrapper, which tints the terminal red as an error card (e.g. "A constructor in each class", "The wrong cast").
* **Toolbox** (`toolbox`): a block of cards, with an optional block nested inside. E.g. "The Java Development Kit" and "The JDK and the JRE".
* **Verdicts** (`verdicts`): examples judged one by one with ✓, ✗ (struck out) or !. No slide uses it at the moment: "Valid or not?" and "Safe or not?" moved to the verdict table.
* **Data table** (`data-table`, `compare-table`): rows revealed by group or one by one. When the rows are examples asked the same questions (attributes, places, objects), all of them show from the start and each row's answers fill in at once, as in the verdict table (e.g. "Four kinds of attribute"); when each row is a question of its own, its label shows first, to ask, and its answers on the next step: all at once, or the known one before the new one in a C and Java comparison (e.g. "Arrays in C and Java", "Abstract class or interface?"). Answers are custom fragments, so the lines stay. A reference table shows by groups instead (e.g. "The eight primitive types").
* **Verdict table** (`data-table verdict-table`, `mark mark-ok|warn|error|none`): one row per example, a question per column answered with ✓/✗ in the verdicts' colors, and the answers of a row filled in at once (custom fragments, the lines stay). Text answers can take a column too, with `mark-start` lining a mark up with them (e.g. "A device of no kind"). E.g. "Valid or not?".
* **Keyword grid** (`keywords`): a list of words in columns, some crossed out. E.g. "Reserved words".
* **Widening chain** (`widening`): types joined by arrows in both directions. E.g. "Type conversion".
* **Phone screens** (`phones`, `phone`, `phone-beside`, `phone-slot`): an iPhone-shaped mobile app screen, the same for every object: the layout is the class, the values each object's own. Unit 2's example is a fictional bank's app, with no name or logo. `phones` sets several side by side (e.g. "Three bank accounts"); `phone-beside` puts one next to a column of cards, and empty fields (`phone-slot`) show the template with no values. A `rule-state` (data) or `rule-behavior` (operations) card, once shown, marks the fields or the buttons in its color (e.g. "The template they share"). `phone-family` shrinks them to set a class (the empty template) and its objects side by side, joined by an arrow (e.g. "Classes and objects"). To act on a screen: `phone-tap` presses a button for one step, `phone-mark` (yellow) or `phone-ring` (a ring) single out a part from a step on, `phone-arrived` makes a field appear and stand out for its step, and `phone-lock` adds a padlock after a value (e.g. "One rate for every account", "Two ways to open an account", "Where do the initials come from?"). A value that changes on a later step goes in a `phone-swap`, the old one as a `fade-out` fragment and the new one as a plain fragment with the same index (e.g. "One rate for every account"). Unit 3's example is a smart home app on the same phone: a device's own screen has its icon in the header disc, `phone-power` (on or off, `phone-power-on` lit), its own panel with a `phone-level` bar (a `<progress>`, its value in the markdown; two of them swap in a `phone-swap-block`) and a `phone-button-wide` across the actions; the template leaves the kind's own part as a dashed `phone-own` box, which a plain card marked `rule-own` colors in its blue once it shows (e.g. "Three smart devices", "What they share"). The home screen lists one `phone-tile` per device, with its status under its name (e.g. "One status per tile").

* **Class hierarchy** (`hierarchy`, `hierarchy-children`, `class-box`, `class-name`, `class-attributes`, `class-methods`): class boxes as in UML, the name, then the attributes (data color) and the methods (operations color), each subclass joined to its superclass by a line ending in a hollow arrowhead. A `hierarchy` holds a box and, optionally, a `hierarchy-children` with one `hierarchy` per subclass, nested for more levels. Siblings take columns of one width and their boxes fill them, so the middle one sits under its superclass's line and the gaps match. Reveal a level by making its `hierarchy-children` the fragment, so its lines come with it. `class-keyword` puts abstract or interface over a name, and `class-box-interface` dashes the box. `hierarchy-row` sets separate hierarchies side by side, each as wide as its own content (e.g. "The collections framework"). E.g. "Superclass and subclasses", "Hierarchies" and "`Object`".
* **File explorer** (`explorer`, `explorer-title`, `explorer-row`, `explorer-folder`, `explorer-java`, `explorer-depth-1` to `3`): a project's folders and files as an editor's side bar shows them, instead of a text tree: open folders with a chevron, `.java` files with a cup, one `explorer-row` per line indented by its depth. A row made a custom fragment is marked while its step is the current one, as the file whose code is appearing. E.g. "Packages".
* **Memory diagram** (`memory`, `memory-frame`, `memory-var`, `memory-link`, `memory-object`, `memory-arrow`, `memory-none`, `memory-row-1` to `3`): the stack's variables and the heap's objects on a grid of fixed rows, under the code that creates them (`memory-layout`, which centers it between the code and the note). Each variable points to its value with a dashed arrow, a reference to its object with a solid one, and `null` ends in a short dashed stub (`memory-none`). `memory-short` (two rows, or three with `memory-rows-3`) with `memory-text` draws small objects on their variable's row, such as strings; `memory-rows-1-2` makes one shared by the first two rows. E.g. "What `new` does in memory" and "Two ways to create a `String`".
* **Exercise list** (`rules rules-grid rules-pair` with linked titles): a slide titled "Exercises" at the end of the section after which some of the unit's exercises in `../code/` can be solved, one card per exercise, its title a link to the task's folder on GitHub and a line on what it practices. Only exercises: the lab assignments are handed out apart. E.g. the two "Exercises" slides of unit 3.
* **Code variants**: `code-build` writes a block line by line (the lines after the highlighted one stay hidden; see the comment in "One name, several versions" for the index anchors it needs); `code-compact` and, smaller still, `code-dense` fit long or many lines.

## Content rules

* Keep text light per slide: if you notice you're adding more than ~5-6 cards or items, or a code block over ~15-18 lines, consider splitting it into several slides (vertical `--` if it's a continuation of the same point, horizontal `---` if it's a new point) instead of shrinking the font or cramming the layout.
* All example Java code must compile and make sense as shown; avoid pseudocode unless the instructor explicitly asks for it.
* From unit 2's "Constructors" on, where `this` is introduced, code reaches the object's own attributes and methods through `this` (`this.balance`, `this.deposit(amount)`) even with no name clash; static ones go by their name alone. The slides before it write them without `this`, which they have not seen yet. `../code/` follows the same rule.
* From unit 3's "Private attributes" on, attributes are `private` and classes, constructors and methods `public`, unless the slide is about another modifier. The slides before it use no modifiers but `public static void main`. `../code/` follows the same rule.
* Code that belongs to a class (attributes, constructors, methods) is shown as the whole class, with what does not matter on the slide folded into a comment such as `// constructor and getter, as before`; never a method on its own. Code that uses the classes is a whole `Main` the first time in a unit, and just the statements after that (they go inside `main`). A file name over each block (``#### `Light.java` ``) when a slide shows more than one file.
* Use speaker notes (`Note:` at the end of a slide) for the extended explanation the instructor will say out loud but doesn't want on screen. It's the natural place to park context from raw notes that shouldn't appear on the slide itself.

## Implementation rules (no patches, no anti-patterns)

These are non-negotiable. If a request seems to need one of the things forbidden here, the structure is wrong: stop and say so instead of forcing it.

**Content never lives in CSS.** Never use `content: "some text"` or `content: var(--something)` to put words on a slide. Text set that way can't be selected or copied, doesn't exist for a screen reader, and exports unpredictably to PDF. Slide text belongs in the markdown; text repeated across every unit (e.g. course name, author, degree) belongs in the single config object in `theme/cover.js`. `content: ""` for a purely decorative shape is fine.

**Never fight reveal.js.** Do not use `!important`, do not inflate a selector to outrank a reveal.js rule, and do not override `position`/`display` to undo what reveal.js set. Do not style reveal's own internals (`.reveal .slides > section::after`, `.slide-background`, `.progress`...) beyond the variables already wired up here. Needing any of these means the markup is wrong: add your own class to the slide and style that instead.

**Real layout, not tuned spacing.** Position blocks with flex or grid. A stack of hand-tuned `margin-top` values that happens to land in the right place is a patch: it breaks the moment the text length or the canvas changes.

**No magic numbers.** Any value that positions something (e.g. `29%`, `63px`) gets a named variable in `:root` with a comment saying what it's for. Sizes are `em` against `--slide-font-size` so the deck rescales as one; the only absolute values in the whole theme are the ones under "Deck geometry" and the `--cover-*` sizes and gaps that lay out the cover.

**Comment and formatting style.** Keep comments short: say what something is or warn about a trap, never a paragraph explaining the reasoning. One line when it fits in about 100 characters; if it really needs more, a second line split at a natural break. One space before a trailing comment in CSS and JavaScript, two in YAML (yamllint's default), never padding to align them in a column. Section headers are plain (`/* Base */`) with a blank line either side, not ruled off with dashes. Double quotes, not single. No em dashes.

**One source of truth.** Anything that appears on more than one slide is defined once. Never solve repetition by copy-pasting into each unit file.

**Deck geometry is not CSS.** Canvas size and reveal.js options go in `reveal-md.json5`. Keep that file as JSON plus `//` comments explaining each setting (no trailing commas): `scripts/config.mjs` reads it to size the PDFs and screenshots.

**Two PDF versions, two shapes.** The class PDF (`npm run pdf:class`) is 16:9, the canvas, with a page per step. The print PDF (`npm run pdf:print`) is 4:3, for paper: same width, `printHeight` high, with every step on one page. Every slide has to work in both, so lay it out with the stage (content from the top, note at the bottom) and never tie a position to the 16:9 height. If the canvas changes, rescale the values under "Deck geometry" and the `--cover-*` sizes and gaps by that same factor: they are the only absolute lengths in the theme, and everything else is an em of them.

**Verify, then say what you couldn't verify.** Before claiming a change works, look at it: `npm run preview` screenshots every slide in its final state into `production/preview/screen/<unit>/`, and `npm run preview -- print <unit>` or `class` shows the PDF pages. Read the images that the change touches, and check the print version too, which is 4:3, whenever a slide has fragments, highlights or a bottom note. What screenshots can't show (animation between steps, other browsers) stays unverified: say so plainly and say what to look for.

**`reveal-md.json5` is read once, at startup.** Watch mode doesn't pick it up. Any change to the canvas, scripts or css means restarting `npm run dev`.

## Expected workflow

1. The instructor gives you loose notes or dictates what they want to cover, sometimes via `/new-slide`, sometimes pasted directly in chat.
2. You decide the unit, the slide type, and generate it in its place within the unit: inside its section, before the summary (if the unit doesn't exist yet, create it with `/new-unit` or ask for its number/name before improvising one).
3. The instructor reviews locally (`npm run dev`, see `README.md`) and asks for specific tweaks, to content or style (`/change-style`).
4. In the same turn, bring the unit's lesson in `../code/` in line with what changed, as "Keeping `slides/` and `code/` in step" in the repository's `CLAUDE.md` describes, and say what you changed there. `/sync-unit` checks a whole unit at once.

Don't renumber or reorder existing slides without being explicitly asked: the instructor may already have rehearsed the lecture around that order.
